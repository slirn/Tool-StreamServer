# M2 · RTMP 推流接入与基础 HLS 拉流 · Plan

- 状态：**已批准，执行中**（2026-08-27 用户批准方案与本机安装 ffmpeg）
- 分支：feature/m2-rtmp-hls

## 1. 背景与目标

- 背景：M1 骨架就绪，模块只有接口没有实现；ADR-001（Node-Media-Server 封装）需落地。
- 目标：OBS/ffmpeg 推 RTMP 流，播放端通过 `http://host:8000/live/<key>/index.m3u8` 拉到 HLS。
- 验收标准：
  1. 端到端：ffmpeg 推流 30s → m3u8 可访问且分片持续增长 → 断推后流从注册表清除；
  2. lint/test/build 全绿，架构守护持续通过（NMS 不泄漏进 core）；
  3. 优雅关停（SIGINT → 断开推流、清理分片目录）。

## 2. 调研结论（决策依据）

- NMS 4.3.2：CommonJS、`engines: node>=18`（Node 24 兼容）、自带 express/ws（自起 HTTP 服务）。
- HLS 由 NMS spawn 的**外部 ffmpeg** 完成（hlsFlags 可配）——本机需装 ffmpeg（已批准）。
- 官方 `@types/node-media-server` 停在 2.3.7，与 v4 脱节 → 自写最小 `.d.ts`。
- 鉴权钩子 `on_prePublish` 原生支持，对上 AuthPolicy 接口；M2 直通放行，M3 接实现。

## 3. 方案设计

NMS 是全家桶（RTMP+HTTP+HLS 编排一体），不强拆，**整体包在 ingress 适配层内**：

```
src/ingress/nms-server.ts     ← 唯一 import NMS 的地方（架构测试守护）
  ├─ 起NMS(rtmp+http+hls config)
  ├─ postPublish/postUnpublish ──► core: MemoryStreamRegistry + 事件总线
  └─ on_prePublish ──► auth 钩子点（M2 直通，M3 接 AuthPolicy）
src/core/registry.ts          ← 纯 TS 实现 StreamRegistry（无第三方依赖）
src/types/node-media-server.d.ts ← 最小类型声明
src/index.ts                  ← 装配：config → registry → nms-server → 信号处理
```

HLS 细节：`hlsFragmentSec→hls_time`、`hlsWindowSize→hls_list_size`、`delete_segments` 自动清旧分片；媒体根目录 MEDIA_ROOT（新增配置，默认 ./media，入 .gitignore）。

## 5. 测试计划

- 单元：registry（publish/unpublish/重复 streamKey/list 快照）；MEDIA_ROOT 穿越拒绝。
- 集成（ffmpeg 门控）：spawn 服务 → ffmpeg 推 testsrc 30s → m3u8 出现且分片 ≥2 → 断推 → registry 清空 → 无残留退出。
- CI（ubuntu 自带 ffmpeg）完整跑 e2e；本地未装时 skip 并打印原因。

## 6. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| NMS 在 Node 24 运行时兼容未实测 | 适配器隔离；可锁 4.2.x；e2e 兜底 |
| 自写 d.ts 与实际 API 偏差 | 只声明用到的方法面；e2e 校验真实行为 |
| 重复 streamKey 竞争 | registry 单测固化：拒绝第二次 publish |
| 本机 ffmpeg 安装失败 | e2e 门控 skip，单测照常，CI 兜底 |

备选被否：自研 RTMP 解析（违背 ADR-001）；srs/golang（违背 ADR-002 跨栈）。
